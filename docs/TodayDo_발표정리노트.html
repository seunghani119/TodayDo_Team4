TodayDo 코드 이해와 발표 정리노트

이 노트는 현재 솔루션의 실제 코드를 기준으로 작성했습니다. 발표의 중심은 일정을 저장하고, 장소와 활동 시간에 맞는 날씨를 조회한 뒤, 준비에 도움이 되는 조언을 제공하는 과정입니다. AI 모델은 claude-sonnet-4-5로 설정되어 있습니다.

1 발표를 시작하는 한 문장

“저희 TodayDo는 일정 관리에 장소별 시간별 날씨와 AI 준비 조언을 연결한 WPF 데스크톱 프로그램입니다.”

2 전체 구조를 먼저 이해하기

사용자 일정→서버와 실제 예보→Claude 조언→화면 표시
구성 맡은 일
TODOList.Client 사용자가 보는 화면과 버튼 처리. 서버에 HTTP 요청을 보내고 결과를 표시합니다.
1103_4조TODOList.Server 입력 검증, DB 저장, 날씨 조회와 AI 조언 요청을 처리합니다.
MySQL 회원, 일정, 장소 데이터를 저장합니다.
RegressionChecks 실제 DB를 바꾸지 않는 요청 전달·날씨 변환·오류 처리 검사와 선택적인 AI 연결 검사를 실행합니다.

화면이 DB에 직접 연결되는 구조가 아닙니다. 화면은 서버 API를 호출하고, 서버가 DB와 외부 API를 다룹니다. 서버의 API 키는 클라이언트로 보내지 않습니다.

발표할 때는 “화면 → 서버 → DB 또는 외부 서비스 → 화면” 순서로 설명하면 됩니다. 현재 클라이언트는 XAML과 코드 비하인드를 사용하는 구조이며, 완전한 MVVM 구조로 구현됐다고 설명하면 안 됩니다.

4 일정 한 건이 저장되는 과정

  1. 사용자가 제목, 내용, 시작/종료 날짜·시간, 장소를 입력합니다.
  2. ReadEditor()가 입력값을 검사하고 TodoInfo를 만듭니다.
  3. 새 지도 장소가 있으면 ResolveTodoLocationAsync()가 장소를 먼저 저장해 LocationID를 받습니다.
  4. ApiService.CreateTodoAsync()가 POST /api/Todo/{memberId}로 일정을 보냅니다.
  5. TodoController.Create()가 회원 존재와 일정 입력값을 다시 검사합니다.
  6. AppDbContext가 일정을 MySQL에 저장합니다.
  7. 저장 성공 후 클라이언트가 최신 목록을 다시 받아 표시합니다.

발표 문장: “클라이언트에서 한 번 검사하고, 서버에서도 다시 검사합니다. 화면 입력을 통과했다고 DB에 바로 저장하지 않습니다.”

수정은 PUT /api/Todo/{memberId}/{todoId}, 삭제는 DELETE /api/Todo/{memberId}/{todoId}를 사용합니다. 저장 성공 뒤 목록 재조회만 실패한 경우에는 ‘저장 실패’로 오해하지 않도록 별도로 안내합니다.

5 지도에서 고른 위치가 날씨 지역이 되는 과정

  1. MapWindow가 WebView2에 map.html을 엽니다.
  2. 사용자가 검색 결과나 지도 위치를 선택하면 HTML이 이름·주소·위도·경도를 보냅니다.
  3. C#이 메시지 출처, 좌표 범위, 주소를 검증합니다.
  4. 사용자가 위치 선택을 확정하면 메인 창이 MapLocationInfo를 받습니다.
  5. 장소 저장 API에서 KmaGridConverter.ToGrid()가 위경도를 Nx·Ny로 바꿉니다.
  6. 일정에는 장소 전체를 복사하지 않고 LocationID로 연결합니다.

발표 문장: “지도는 위도·경도를 쓰지만 기상청은 격자 좌표를 쓰기 때문에, 중간에 좌표 변환이 필요합니다.”

6 시간별 날씨를 조회하는 과정

  1. 일정 선택 또는 상세 창의 날씨 새로고침에서 요청을 시작합니다.
  2. GET /api/Weather/todos/{memberId}/{todoId}가 해당 회원의 일정과 장소를 확인합니다.
  3. 서버가 한국 시간과 기상청 발표 시각을 기준으로 사용할 예보를 정합니다.
  4. ReadForecastAsync()가 기상청 응답을 페이지별로 읽고 활동 시간에 필요한 항목만 추립니다.
  5. TMP·POP·PCP·SKY·PTY를 기온·강수확률·강수량·하늘·강수 형태로 묶습니다.
  6. 화면에서 읽을 수 있는 코드·단위 문구로 바꾸고 조회 상태와 함께 반환합니다.

예: 시작 09시, 종료 11시인 일정은 09시와 10시 예보를 확인합니다. 종료 시각이 다음 활동 구간까지 중복 포함되지 않도록 처리합니다.

상태 의미
ready 전체 활동 시간의 필요한 예보 항목이 채워졌습니다.
partial 일부 시간 또는 항목만 제공됩니다.
pending 조회 가능한 활동 예보가 아직 없습니다.
past 과거 일정으로, 저장된 예보 이력이 필요합니다.
location_required 일정의 장소를 먼저 정해야 합니다.

발표 문장: “예보가 없을 때 임의로 날씨를 만들지 않고, 대기·일부 제공·지역 미선택 상태를 구분해 보여줍니다.”

7 AI 조언과 코드의 역할 구분

POST /api/Weather/todos/{memberId}/{todoId}/advice를 호출하면 서버가 저장된 일정과 날씨를 다시 조회합니다.

코드가 하는 일: 사용자 입력, 장소, 활동 시간, 시간별 예보와 예보 제공 상태를 Claude에 전달합니다. 기상청 코드를 읽기 쉬운 문구로 바꾸며, 활동을 미리 분류하거나 적합도를 정하지 않습니다.

Claude가 하는 일: 사용자가 입력한 제목과 내용을 직접 읽고 실제 예보에 맞는 준비물과 유의점을 조언합니다. 예보가 없거나 일부만 있으면 해당 상태도 전달하며, 프롬프트에서 없는 날씨를 추측하지 않도록 요청합니다.

응답 처리: 통신 실패, 완료되지 않은 응답과 빈 답변을 검사합니다. 정상 답변은 숫자나 키워드로 걸러 기본 안내로 바꾸지 않고 그대로 표시합니다.

발표 문장: “사용자가 입력한 일정과 기상청 예보를 AI가 직접 읽고 조언합니다. 코드는 자료 전달과 화면 표시, 통신 오류 처리를 담당합니다.”

AI 답변의 정확성을 코드가 보장하지는 않습니다. 원본 예보는 시간별 날씨 탭에서 별도로 확인할 수 있으며, 외부 API 오류는 오류 안내로 표시합니다.

8 자동 갱신과 화면 안정성

코드 장치 필요한 이유
async / await 서버 응답을 기다리는 동안 UI 스레드를 오래 막지 않도록 합니다.
isBusy 저장 요청 등의 중복 클릭을 막습니다.
CancellationTokenSource 일정 선택 변경이나 창 종료 때 진행 중인 요청을 취소합니다.
isClosed와 선택 일정 재확인 늦게 도착한 응답이 닫힌 창이나 다른 일정 화면을 덮어쓰는 것을 막습니다.
editorBaseline 스냅샷 저장하지 않은 편집 내용을 감지해 버릴지 확인합니다.
INotifyPropertyChanged TodoInfo의 날씨 요약 변경을 목록 화면에 알립니다.
DispatcherTimer 메인 창에서 30분마다 대상 일정의 날씨를 다시 확인합니다.
previousWeather / weatherNotices 이전 예보와 비교해 달라진 항목을 알리고 최근 알림 10개를 유지합니다.

자동 조회 대상은 미완료이고 장소가 있으며 종료 또는 시작 시각이 지나지 않은 일정입니다. 자동 갱신은 앱이 실행된 동안 동작합니다. 앱을 종료해도 계속 실행되는 서버 푸시 알림 기능은 아닙니다.

9 DB 구조를 설명하는 법

회원 1명→일정 여러 개←장소 연결

회원 한 명은 여러 일정을 가질 수 있고, 장소 한 곳도 여러 일정에서 참조할 수 있습니다. Todo.LocationID는 nullable이라 장소를 선택하지 않은 일정도 존재할 수 있습니다. 클라이언트의 *Info는 통신·화면용 데이터이고, 서버의 Models는 DB 엔티티라는 차이가 있습니다.

10 코드 화면 시연 순서

  1. MainWindow.xaml.cs의 ‘일정 등록 수정 삭제와 재조회’ 구역을 열어 버튼의 출발점을 보여줍니다.
  2. ApiService.cs의 ‘일정 조회 등록 수정 삭제 API’를 열어 HTTP 요청을 보여줍니다.
  3. TodoController.cs의 ‘등록 API’를 열어 서버 검증과 DB 저장을 보여줍니다.
  4. WeatherController.cs의 ‘일정별 기상청 날씨 조회 API’를 열어 일정→장소→예보 연결을 설명합니다.
  5. WeatherDisplayFormatter.cs를 열어 기상청 코드의 표시 문구 변환을 보여줍니다.
  6. AiAdviceService.cs의 ‘예보 검증 Claude 요청과 응답 처리’를 열어 AI의 역할을 마무리합니다.

모든 파일을 처음부터 끝까지 읽기보다 위 여섯 지점을 연결해서 설명하세요. 환경 변수, API 키, 비밀번호, 연결 문자열이 보이는 파일은 화면 공유 전에 닫아 둡니다.

11 약 4분 발표 대본

0분부터 40초 프로그램 소개

“저희는 일정 관리와 날씨 정보를 연결한 TodayDo를 개발했습니다. 사용자는 일정과 장소를 저장하고, 활동 시간의 예보와 준비 조언을 함께 확인할 수 있습니다. 화면은 WPF로 만들었고, ASP.NET Core 서버가 MySQL과 외부 API를 연결합니다.”

40초부터 1분 30초 일정과 장소

12 예상 질문과 답변

질문 답변
왜 클라이언트와 서버를 나눴나요? 화면은 사용자 작업에 집중하고, DB와 외부 API 처리는 서버에서 관리하기 위해서입니다.
partial 파일은 서로 다른 클래스인가요? 아닙니다. 같은 MainWindow 클래스를 기능별 파일로 나눈 것입니다.
AI가 기상 정보를 예측하나요? 아닙니다. 기상청 예보를 조회하고, AI는 제공된 자료로 준비 조언을 작성합니다.
AI 답변을 코드가 다시 판단하나요? 정상 답변은 그대로 표시합니다. 통신 실패와 빈 답변 등 요청·응답 오류를 처리합니다.
30분마다 항상 알림이 나오나요? 대상 일정을 다시 조회하고 이전 예보와 비교합니다. 값이 바뀌었을 때 변경 알림을 만듭니다.
로그인하면 서버 API가 모두 보호되나요? 현재는 앱의 로그인 상태와 회원 번호를 활용하는 구조입니다. 토큰 기반 서버 인증·인가가 완성됐다고 설명하면 안 됩니다.
공원 걷기나 미술관도 처리하나요? 제목과 내용을 그대로 AI에 전달합니다. 키워드로 사전 분류하지 않으며 해석은 AI가 담당합니다.
region을 넣으면 기능이 달라지나요? 아닙니다. Visual Studio에서 코드를 묶어 접고 펼치는 가독성 표시입니다.

13 이번 정리의 변경 범위와 검증

2026년 11월 18일 기준으로 ScheduleAdviceRules의 규칙 판단, 답변 필터, 기본 안내 생성을 제거했습니다. 시간별 날씨 표시 변환은 WeatherDisplayFormatter로 옮겼습니다. 상세 창의 참고 판단과 기준 표시, 삭제한 규칙에 대한 검사도 정리했습니다.

모델과 DB 구조, 회원 및 일정 관리 기능은 유지했습니다. 예보가 없는 응답에도 제목, 내용, 활동 시간을 포함하여 AI가 원문을 읽을 수 있도록 했습니다.
